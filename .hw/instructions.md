# hw v2

主担当が目的・制約・完了条件を把握し、調査・計画・分担を判断する。
計画専任モデル、全タスク共通の工程数、S/M/L の書類は必須ではない。
未知には調査や小さな実験を、失敗の影響が大きい変更には独立検証を追加する。

- 分担するときだけ `.hw/roles/` の該当する手引きを読む。
  調査は利用可能な低費用モデルも候補。設計を左右する根拠は主担当が確認する。
- Builder に目的・業務ルール・制約を渡す。QA の初回判定へ Builder の自己評価や
  他レビュアーの結論を渡さない。受入条件の抜けも元の要求から確認する。
- 小さい仕事は直接進める。複雑な仕事は `.hw/tasks/<id>.json` に要求と制約を保存する。
  実装計画は必要な粒度で既存の計画場所に置く。再開には確定事項と未解決事項を残す。
  元の要求・確認済み事実・採用判断の理由と、主担当の仮説・未承認案を区別する。
  設計案の分岐は必要なときの選択肢。案の数や別モデルの一致を品質の証明にしない。
- 開発途中は `python3 .hw/runtime/hw.py verify`。最終確認は対象 checkout で
  `python3 .hw/runtime/hw.py gate --base <比較先のcommitまたはref>`。
  gate は変更全体を対象とする。検証後に変更したら再検証する。
- 独立レビューの対象なら `.hw/usage.md` の context / review 手順を使う。
  重大な欠陥は契約に未記載でも報告し、合格扱いにしない。好みの変更は提案に留める。
- 新しい体験・仕様の解釈が成否を左右する作業では、意図レビューを検討する。
  有効にする案件だけ task.intent_review.required を true にする。主担当の設計前に
  原文だけで独立した基準を作り、設計と小さな試作を別セッションで評価する。
  `.hw/roles/intent-reviewer.md` と `.hw/usage.md` の段階別入力・ゲートを使う。
  技術QAの合格で代用しない。必須の観測がなければ未確認として止める。
- 同じ失敗を繰り返したら原因を再診断する。テスト・コード・環境・文書のうち
  原因に合う対策を選ぶ。指示追加や台帳の更新だけを解決と見なさない。
- ローカルの合格記録は承認でもエージェントの身元証明でもない。
  本番操作の権限と実行範囲は外部サービス側で制限する。
  `.hw/project.json` の設定や `doctor` の結果だけで保護設定済みと報告しない。
- 既に依頼・承認された範囲の可逆な作業は続ける。業務条件や実行範囲の変更は
  必要な根拠を揃えて判断を返す。報告は結果・実施した検証・未確認事項を日本語で。
